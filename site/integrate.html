Integrate Muster into your live platforms

Muster is one service with several front doors. People ask in the tools they already use; Muster routes each request to SFIA role agents, which act through MCP connections to your systems, inside approval limits set by SFIA level. The code is in assistant/.

Front doors

Pick the places your people already ask for help. Each one starts automatically when its settings are in assistant/.env.

Slack

Built

Mention @Muster in a channel or DM it. Replies go in thread; approvals get Approve and Reject buttons.

  1. At api.slack.com/apps choose Create New App → From a manifest and paste assistant/manifests/slack-app.yaml.
  2. Install it to your workspace and create an app-level token with connections:write.
  3. Add the three tokens to .env and restart. Socket Mode means no public URL is needed.
SLACK_BOT_TOKEN=xoxb-…
SLACK_APP_TOKEN=xapp-…
SLACK_SIGNING_SECRET=…

Microsoft Teams

Built

Chat with Muster or add it to a team. Approvals arrive as Adaptive Cards.

  1. In Azure, create an Azure Bot (single tenant) with messaging endpoint https://YOUR-HOST/api/messages.
  2. Put the app id and secret in .env.
  3. Fill the app id into manifests/teams-manifest.json, add a colour and outline icon, zip the three files, and upload in Teams admin (or Apps → Upload a custom app).
MICROSOFT_APP_ID=…
MICROSOFT_APP_PASSWORD=…
MICROSOFT_APP_TENANT_ID=…

Email (Gmail)

Built

People email a help address. Muster replies in the thread as a draft for a person to send, or sends itself if you allow it.

  1. Create a Google OAuth client with gmail.modify and gmail.compose, and get a refresh token for the help mailbox.
  2. Add a Gmail filter that labels incoming requests Ask-Muster.
  3. Start in draft mode; switch to send once you trust the replies.
GMAIL_CLIENT_ID=…
GMAIL_CLIENT_SECRET=…
GMAIL_REFRESH_TOKEN=…
GMAIL_REPLY_MODE=draft

Outlook / Microsoft 365 mail Planned follows the same pattern through Microsoft Graph. Until then, use Teams or forward to the Gmail mailbox.

Intranet, SharePoint, Confluence

Built

The kelpie sits in the corner of any page. One script tag; no build step.

<script src="https://YOUR-HOST/muster.js"
  data-api="https://YOUR-HOST"
  data-token="YOUR_WEB_TOKEN"
  data-user="Signed-in user's name" defer></script>
  1. Set MUSTER_WEB_TOKEN and add the intranet's address to MUSTER_ALLOWED_ORIGINS.
  2. SharePoint Online blocks inline scripts on modern pages, so wrap the snippet in an SPFx application customizer. Confluence needs an HTML macro or a Forge app, depending on your admin settings.

Jira Service Management

Built (webhook)

New tickets go to Muster; its triage comes back as a comment, and approvals as comments people can answer.

  1. Set MUSTER_WEBHOOK_TOKEN on the server.
  2. Create an Automation rule: Work item created → Send web request to POST https://YOUR-HOST/api/webhook with header Authorization: Bearer YOUR_WEBHOOK_TOKEN and this body.
  3. Add a second rule with an Incoming webhook trigger that comments {{webhookData.text}} on the ticket, and use its URL as callbackUrl.
{
  "source": "jira",
  "conversationId": "{{issue.key}}",
  "user": "{{reporter.displayName}}",
  "text": "{{issue.summary}}\n\n{{issue.description}}",
  "callbackUrl": "YOUR_JIRA_INCOMING_WEBHOOK_URL"
}

ServiceNow

Built (webhook)

An incident or request triggers Muster; its reply lands in the work notes.

  1. Store the webhook token as a system property or credential.
  2. Add an async Business Rule (or Flow Designer REST step) on insert that posts to /api/webhook.
  3. For later updates, expose a Scripted REST API that writes to work notes, and pass its URL as callbackUrl.
var r = new sn_ws.RESTMessageV2();
r.setEndpoint('https://YOUR-HOST/api/webhook');
r.setHttpMethod('POST');
r.setRequestHeader('Content-Type', 'application/json');
r.setRequestHeader('Authorization', 'Bearer ' +
  gs.getProperty('muster.webhook.token'));
r.setRequestBody(JSON.stringify({
  source: 'servicenow',
  conversationId: current.number.toString(),
  user: current.caller_id.getDisplayValue(),
  text: current.short_description + '\n\n' + current.description
}));
var res = JSON.parse(r.execute().getBody());
current.work_notes = 'Muster: ' + res.reply;
current.update();

REST API

Built

For anything else: portals, bots, Power Automate, Zapier, scripts.

curl https://YOUR-HOST/api/chat \
  -H "Authorization: Bearer $MUSTER_WEB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"conversationId":"demo-1","user":"Jane",
       "text":"Is the VPN down?"}'

# Approve a pending action
curl -X POST https://YOUR-HOST/api/approvals/1a2b3c4d \
  -H "Authorization: Bearer $MUSTER_WEB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"approved":true,"approver":"Jane"}'

Other endpoints: GET /api/approvals, GET /api/agents, GET /healthz.

Rovo, Copilot Studio, Claude Code

Configure

Prefer your existing agent platform? Use the 75 agent files without running Muster.

  1. Claude Code: copy agents/ and orchestrators/ into .claude/agents/.
  2. Atlassian Rovo: create one Rovo agent per role you need; paste the agent file's body as its instructions and turn on the Jira and Confluence actions it lists.
  3. Microsoft Copilot Studio: one agent per role, the body as instructions, and the MCP servers from its Tools section added as connectors.
  4. Use a family orchestrator file as the routing agent.

You lose Muster's SFIA-level approval gates, so set each platform's own approval settings to match.

Connect the tools agents use

Agents act through MCP servers. Each role only sees the servers recommended for it and enabled in assistant/config/mcp-servers.json.

"gh":  { "enabled": true, "transport": "http",
         "url": "https://api.githubcopilot.com/mcp/",
         "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" } },
"atl": { "enabled": true, "transport": "http",
         "url": "https://mcp.atlassian.com/v1/mcp",
         "headers": { "Authorization": "Bearer ${ATLASSIAN_TOKEN}" } }

Start every server with a read-only account or token. Tools are classed as read, write or destructive from the server's own hints, falling back to the tool's name, and unknown tools count as writes.

Roll out in four steps

Weeks 1–2Shadow

One channel, read-only tools, agents at level 2. Muster answers and recommends; it changes nothing. Review the audit log weekly.

Weeks 3–6Approve

Raise service desk and operations agents to level 3–4. Every change needs a person's OK. Track approval rates and rejected actions.

Weeks 7–10Delegate

Where approvals are always yes, raise those agents to level 5 for writes. Destructive actions still always ask.

AfterScale

Add channels and capability areas one at a time. Move memory and approvals to a database before going organisation-wide.

Content from emails, tickets and tools is treated as information, never as instructions, but prompt injection is a real risk for any agent that can act. Keep write-capable agents on approvals until you've watched them work, and limit each MCP token to what its role needs.
